# Offline recommendation queue tasks

Requires Hooka **1.5.2+**. This compatible recommendation preset task pack uses a
patch changeset. It extends the existing registry/queue without changing their
contracts, adding a service, calling a provider or installing a scheduler.

## Same Sharelink worker

The `toss-sharelink` preset includes both `@hooka/pack-toss-sharelink` and
`@hooka/pack-recommendations`, with capabilities `toss-sharelink,recommendations`.
No separate preset/container is required. Other custom workers may install the
`recommendations` capability independently. It requires only Bun, not Toss keys.
The image's capability manifest is generated by the existing install mechanism.
An explicit `HOOKA_INSTALLED_CAPABILITIES` override must include `recommendations`
to claim these jobs; an old `toss-sharelink`-only override keeps them queued.

Installing/upgrading the image creates no recommendation jobs. All actual queued
operations require exact `HOOKA_RECOMMENDATIONS_TASKS_ENABLED=true`. This is
independent of `HOOKA_SHARELINK_RECOMMENDATIONS_ENABLED`: learning/publication
can run offline while live product ordering stays off. Existing recommendation
CLI behavior and Sharelink matching/scheduling remain unchanged.

Set operator-owned absolute paths on the owning worker:

| Environment | Purpose |
| --- | --- |
| `HOOKA_RECOMMENDATIONS_CONFIG_PATH` | Reviewed registration JSON |
| `HOOKA_RECOMMENDATIONS_DB_PATH` | Explicitly initialized private local SQLite file |
| `HOOKA_RECOMMENDATIONS_INBOX_PATH` | Existing backend artifact inbox directory |
| `HOOKA_RECOMMENDATIONS_RESULTS_PATH` | Existing private app outbox directory |
| `HOOKA_RECOMMENDATIONS_TASKS_ENABLED` | Defaults off; exact `true` enables queued execution |

DB operations verify the application marker/schema read-only before opening a
writer. Missing, blank or foreign stores are rejected without initialization.
Use `hooka recommendations init --domain <private-file>` explicitly first. Inbox
and outbox roots must already exist and must not overlap. The DB must be outside
both roots and any configured Sharelink results directory, and must be a different
file from the registration, Hooka queue and Sharelink DB (hardlink aliases also
reject). Keep these files/volumes private to trusted workers; never mount a
consumer database or network SQLite volume. SQLite readers may require writable
WAL side-file access despite making no logical DB changes.

Configuration is read-only. Backends can atomically publish only their own inbox
files; consumers can read only their own outbox. Consumers cannot write the
outbox. The local operator owns the queue and all bindings. These jobs are not
an app-authenticated ingress endpoint: do not give a browser/mobile client the
Hooka admin/webhook secret or accept unreviewed queue inputs from it. A scoped
cross-host transport/importer remains future work.

The optional [task overlay](../../examples/toss-sharelink/compose.recommendations-tasks.yml)
adds only mounts and environment to the existing worker. It leaves the older
ranking-only overlay usable by itself. Prepare the external private model/outbox
volumes and existing inbox/config directories, then review configuration:

```sh
docker compose -f compose.yml -f compose.recommendations.yml -f compose.recommendations-tasks.yml config --quiet
```

This command starts no container. Do not enable actual jobs until the model owner,
backend artifacts and app permissions are reviewed. Use one owning updater per
learning group. Multiple workers cannot rely on queue insertion order for
pipeline dependencies. Build/ingest are synchronous bounded SQLite operations;
large builds can delay a same-worker Sharelink job and its heartbeat. Set
`HOOKA_RUN_LEASE_MS` above the measured worst-case execution time before scaling
input sizes. A separate worker is an optional capacity choice.

## Task inputs and artifact layout

No task input contains a filesystem path, raw rows, provider URL or credentials.
Schemas are separate additions in `docs/contracts/recommendations/tasks/v1/`;
existing recommendation and Sharelink v1 artifact contracts are unchanged.

| Task | Input | Output in private queue history |
| --- | --- | --- |
| `recommendations.validate` | `configDigest` | Registration counts/digest; no DB required |
| `recommendations.ingest` | `configDigest`, `appId`, `artifactId`, `artifactDigest`, `kind` (`manifest`/`aggregate`) | App and applied/duplicate/stale status |
| `recommendations.build` | `configDigest` | Model ID, generated time, row count |
| `recommendations.plan` | `configDigest`, `appId`, `artifactId`, `artifactDigest`, `modelGenerationId` | App/request/decision/model IDs and candidate count; no writes |
| `recommendations.export` | Same as plan | Recorded decision's app-scoped publication pointer |
| `recommendations.status` | `{}` | Private current generation, freshness/counts/coverage |
| `recommendations.prune` | `{}` | Pruned-day count; existing replay protections retained |

`configDigest` is `digest(configSchema.parse(configJSON))`, computed using the
exported canonical SHA-256 `digest` helper. `artifactDigest` is `digest(parsedJSON)` before contract
default normalization. These are canonical semantic JSON digests, **not** hashes
of file bytes: whitespace/object-key order does not matter, array order does.
Both are 64 lowercase hex characters. Example offline preparation from `/app`:

```sh
bun -e 'import {configSchema,digest,readArtifact} from "@hooka/pack-recommendations"; const c=configSchema.parse(await readArtifact(Bun.env.HOOKA_RECOMMENDATIONS_CONFIG_PATH,2097152)); console.log(digest(c));'
# Repeat with digest(await readArtifact(artifactPath,8388608)) for the exact inbox file.
```

Artifact IDs/app IDs use the existing bounded ID grammar. Files are read from:

```text
<inbox>/<appId>/manifest/<artifactId>.json
<inbox>/<appId>/aggregate/<artifactId>.json
<inbox>/<appId>/request/<artifactId>.json
```

Files should be immutable once referenced. The worker rereads and hashes them
on every attempt; a changed digest or registration is terminal. Reads are bounded
at 8 MiB for ingest and 2 MiB for registration/requests. App ID, producer ID and
available app revision must agree with current registration. Assignment lineage,
profile/window relationships, revisions and completed/sealed days remain checked
by the existing store. Invalid batches do not partially apply. Symlinks below app
inbox/outbox roots are rejected. The approved roots themselves can resolve through
operator-owned aliases; do not allow producers to mutate their parent directories.

Plan/export additionally pin the expected **current** model generation. If the
model pointer moves before execution, the job fails rather than silently choosing
new weights; prepare a newly reviewed payload for the new model. The export check
also runs inside the decision transaction before recording a decision. It does
not serve retained historic models after they stop being current.

## Controlled pipeline and retries

1. Publish immutable app manifests and complete UTC-day aggregates atomically.
2. Validate the reviewed config, enqueue manifest ingest, and wait for success.
3. Enqueue aggregate ingest and wait for success. Same revision/digest is a no-op;
   higher revisions replace the entire day, never increment counts on retry.
4. Build a new sealed generation after all required ingests succeed.
5. Produce an expiring app request, bind its digest/config/current model, review
   with `task run ... --dry-run`, then explicitly enqueue export if wanted.
6. Inspect the publication/consumer validation and periodically enqueue prune.

The existing operator-controlled scheduler/cron can enqueue these tasks, but this
pack does not chain/enqueue jobs or create a recurring schedule. Wait for each
prerequisite's terminal success; do not merely enqueue the entire pipeline and
assume FIFO across workers. A live export applies no consumer placement itself.
Consumers still validate the exact request, expiry, pointer and result before use.

An operator-reviewed queue payload has this shape (replace placeholder hashes/model IDs):

```json
{
  "configDigest": "<64-lowercase-hex-registration-digest>",
  "appId": "cats",
  "artifactId": "request-2026-10-06-low",
  "artifactDigest": "<64-lowercase-hex-artifact-digest>",
  "modelGenerationId": "<reviewed-current-model-id>"
}
```

```sh
hooka task run recommendations.export --config-digest <config-hash> --app-id cats --artifact-id request-2026-10-06-low --artifact-digest <artifact-hash> --model-generation-id <model-id> --dry-run
# Enable HOOKA_RECOMMENDATIONS_TASKS_ENABLED only after review; then explicitly enqueue.
hooka task enqueue recommendations.export --config-digest <config-hash> --app-id cats --artifact-id request-2026-10-06-low --artifact-digest <artifact-hash> --model-generation-id <model-id> --db /data/hooka.sqlite
hooka run watch <returned-run-id> --db /data/hooka.sqlite
```

Dry runs do not need the enablement flag. They load/validate the bound config,
paths and artifact envelope/hash using read-only stores. Plan/export dry runs also
score against the pinned model. Ingest dry runs **do not** run the store's full
assignment/aggregate transaction checks; `semanticIngestChecked=false` makes this
explicit. Build/prune dry runs do not derive/prune evidence. Only actual execution
proves those operations succeeded. Use the offline CLI for full scoring weights
and sampling previews; plan/export summaries intentionally omit weights and raw evidence.

SQLite busy/locked and selected transient resource errors are retryable using
existing backoff/dead-letter rules. Missing artifacts, invalid contracts, changed
hashes/models, permission errors and revision conflicts are terminal; inspect
privately, fix inputs and submit a new reviewed job. Errors in queue history are
sanitized and contain no artifact contents/paths. Failed learning leaves existing
Sharelink offers usable and does not consume provider budgets.

Exports reuse deterministic decisions and immutable files. A failed publication
can retry against the same request/config/model while still current and unexpired.
If any binding changes, review a fresh payload instead. The store's writer lock
protects the final pointer commit; conflicting/older pointers cannot replace
newer publications. Disabling `HOOKA_RECOMMENDATIONS_TASKS_ENABLED` prevents
subsequent tasks from executing; already-running transactions can finish. It
retains models, evidence, app towers, manual links and current offers.
